PID-free device identity architecture
-------------------------------------
The active Setup production path no longer contains any endpoint PID constant
that assigns a product identity or a wired/wireless role.

Present Razer endpoint PIDs are discovered generically from VID 1532 PnP/CIM,
registry and DriverStore evidence. For each present PID, Setup Scanner 1.0.3
queries only the physical USB root with Get-PnpDeviceProperty and prefers
DEVPKEY_Device_BusReportedDeviceDesc as the identity. Matching normalized bus
identities are grouped into one end product even when the observed connections
use different PIDs or ContainerIds.

The prior VerifiedConnectionTypes table and the four-state BlackWidow PID-role
marker are removed from active production code. The old scanner source is kept
only under docs/setup-history and is not part of the embedded Runtime/setup
production payload.

Generic connection-role learning
--------------------------------
Connection role is evidence/confidence based rather than PID based:
- explicit dongle/receiver or wired/cable transport text => HIGH confidence;
- paired HID-collection topology asymmetry => MEDIUM confidence;
- a later one-path/two-path transition of the same learned pair can promote the
  established topology roles to HIGH confidence;
- equal-rank contradictory non-explicit evidence => role-evidence-conflict and
  generic usb-device; no guessed role is emitted.

Persistent app-owned learning is stored in:
  Setup/RazerConnectionHistory-v1.json

Observed PIDs are stored there only as runtime data/fingerprint keys. Reuse of a
historical role is guarded by matching productKey, so a reused PID cannot import
an unrelated product's role.

Performance architecture
------------------------
The diagnostic 1.0.3-identity-debug prototype queried many properties for every
HID/USB interface and was intentionally slow. Production Setup Scanner 1.0.3
uses one root-only Get-PnpDeviceProperty call per present PID. HID collection /
interface counts are computed from the Get-PnpDevice enumeration already needed
by the normal scanner, avoiding the deep per-interface property sweep.

Native evidence represented by the generic algorithm
----------------------------------------------------
The controlled v2.2.3 identity experiments showed that the two simultaneously
present connection paths of the tested Viper model shared one bus-reported
product identity while exposing HID collection counts 5 vs 6. The tested
BlackWidow model likewise shared one bus-reported product identity while
exposing HID collection counts 7 vs 10. The production implementation encodes
neither product name nor PID; it only uses the generic identity/topology rules.

Unchanged health/evidence architecture
--------------------------------------
Health Engine 1.4.2 remains capability-driven and read-only. The v2.2.3
PRIMARY/RUNTIME/SUPPORTING AppEngine evidence-role architecture is unchanged.
Gates 7, 10 and 11 remain direct-source driven; SUPPORTING log evidence cannot
independently promote health severity.
