Native v2.3.0 bug evidence
--------------------------
The first native Windows acceptance run of v2.3.0 showed:
- RegisterDeviceNotificationW registration succeeded.
- the startup fast live refresh then failed before presence publication with:
  "Cannot overwrite variable PID because it is read-only or constant."
- root cause: PowerShell variables are case-insensitive. Local write targets named
  $pid in setup-razer-live-v1.0.0.ps1 collided with the read-only automatic $PID
  process variable.

Mandatory RED -> GREEN regression proof
---------------------------------------
RED on the unmodified v2.3.0 production source before the fix:
- setup/setup-razer-live-v1.0.0.ps1: one direct $pid assignment
- setup/setup-razer-live-v1.0.0.ps1: three foreach($pid ...) write targets
- health-engine-v1.4.2.ps1: one latent fallback $pid assignment in
  Test-ConnectionUsesRazerStack
- targeted regression guard result: FAIL as required

GREEN after the v2.3.1 fix:
- Fast Live Probe 1.0.1 uses $devicePid for all local PID variables.
- Health Engine 1.4.3 uses $devicePid in the same fallback; gate/evidence semantics
  are unchanged from 1.4.2.
- tools/test_powershell_reserved_pid.py now discovers actual production payloads
  from runtime embed references plus active setup/repair payloads and rejects any
  future assignment/foreach target colliding with reserved $PID.
- build.sh executes this regression guard before all other validators.
- targeted regression guard result: PASS.

v2.3.1 live/device-change architecture
--------------------------------------
Unchanged from v2.3.0 except for the PowerShell reserved-variable fix:
- persisted presentAtScan is historical until a current-session live refresh succeeds
- startup with a valid inventory automatically runs the known-PID PresentOnly probe
- known-PID live refresh avoids Registry history, DriverStore and INF traversal
- current USB-root product identity must verify to stored productKey before presence
  publication
- RegisterDeviceNotificationW / WM_DEVICECHANGE events only trigger debounced
  re-verification and are never identity/role evidence
- probe-level errors fail closed
- Acid Green means current verified live presence only
- legacy inventories can recover mouse/keyboard presentation from stored PnP/HID
  evidence without PID/model mappings or persistence rewrite

Guided connection learning
--------------------------
Unchanged from v2.3.0:
- product-specific fast baseline -> wait for Windows device event -> target delta probe
- target probe may discover a previously unknown present PID only after current root
  identity verifies to the selected productKey
- Wired requires exactly one new verified connection
- Wireless excludes the already-known HIGH wired connection and requires exactly one
  remaining verified target connection
- ambiguity, weak identity or explicit descriptor-role conflict writes no history
- passive topology/incidental-transition role production remains disabled
