# RHC — Source Delivery Contract

**Source authority is Git.** A distributable application version must correspond to a reproducible, independently buildable, immutable versioned Git source tag pointing at the verified `sourceSha` in `downloads/releases.json`/`downloads/latest.json`. The complete source includes Go, Windows PowerShell diagnostic/repair payloads, PE resources, assets, locales, validators, build scripts and necessary documentation. Do not use the latest main commit or a Markdown release heading in place of the manifest-to-source-tag comparison.

**One public Portable package:** The current release allowlist contains seven runtime files inside an immutable lean `downloads/RazerHealthCenter-Portable-vX.Y.Z.H.zip`, with `X.Y.Z.H` derived from live `model.go` and the release catalog. No nested ZIP, separate downloadable Source ZIP, nonruntime logs/forensics or additional standalone EXE is required. Existing source packaging/reproducibility test fixtures may be retained for nonpublishing historical regression but do not define the current release download topology.

**Source and package publication can have separate PRs.** An independently qualified source-version PR may merge first for the owner-authorized interim workflow; a separate four-file public download PR then links its **sourceSha**, source PR and owning Issues. The signed/certified standard production controller may require its own atomic source-plus-downloads transaction. The applicable executable contracts, hosted Linux and native Windows PowerShell 5.1/Razer repair safety, deterministic PE/ZIP verification, immutable prior versions, catalog and source tag must independently pass. See [Release Process](docs/RELEASE_PROCESS.md).

**Standing interim boundary:** the owner permits qualified unsigned/uncertified interim releases until expressly revoked, with actual physical Razer device tests, rollback and publisher/SmartScreen trust still DEFERRED/NOT_VERIFIED. This does **not** activate the separately fail-closed standard signed-production policy or imply verified hardware/trust.

For the version-to-source-to-PR-to-Issue reconstruction and the mandatory Issue-backed PR process for **all future file changes**, see [Git Provenance](docs/GIT_PROVENANCE_CONTRACT.md). Version-specific source deliveries, previous superseded Source ZIP decisions, hashes and release rationale are preserved in the responsible GitHub Issues/Rolling Comments and merged Git history, not duplicated here.
