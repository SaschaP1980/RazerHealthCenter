The full v3.0.8.25 branchless release succeeded: Candidate #38791921204 (3 genuine jobs), Publisher #38792221663 (4 genuine jobs and Candidate PE reuse), staged Downloads #38792456202 (1 genuine job), independently public HTTPS/native Windows RHC-102 #38792553031 (3 genuine jobs). The autonomous [RHC158 closure #38792695559 attempt 1](https://github.com/SaschaP1980/RazerHealthCenter/actions/runs/38792695559) **failed**, not because any source/release gate failed, but because `rhc190_fast_closure.close_fast` attempted the audit comment `g.api("POST",...)` while its real inherited `GitHubGateway.api` rejected any verb other than GET/PATCH. The catch-and-readback logic correctly refused an unaudited Issue close, but the missing transport prevented first-try autonomous closure. The old sanitized `ELIGIBILITY_OR_AUDIT_BLOCKED` diagnostic alone did not reveal the exact predicate; this transport mismatch is confirmed directly in source and covered by focused RED tests.

An owner-authorized **manual authenticated single audit** comment #6206775424 followed by rerunning **only** the failed Closure job led to attempt 2 SUCCESS with full four-gate revalidation and RHC-204 closed/completed at 2026-10-16T02:37:25Z. The historical attempt 1 remains FAILED and the measured `publisher_to_issue_close_seconds=26388` includes recovery; it cannot be claimed as normal release performance.

## Narrow transport and threat model

`tools/rhc158_release_closure.py:Gateway.create_fast_audit_comment(number,body)` is the **only** new authenticated Fast closure write capability. The generic `tools/rhc139_rolling_audit.py:GitHubGateway.api` remains **GET/PATCH only**, with no broad POST or `pull_request_target` and no new GitHub token/App/PAT.

The call originates only from `tools/rhc190_fast_closure.py:close_fast` **after** all existing immutable source/tag/main/PR, responsible Issue label/dev-path and **four independently genuine completed-success workflows and job inventories** pass. The outgoing audit body must be exactly canonical `RHC190_FAST_CLOSURE=<sorted JSON>`, with seven exact permitted fields: correct positive bound Issue and PR, a four-component version, exact 40-character source and main SHAs, the static `ACTUAL_CANDIDATE_3_PUBLISHER_4_DOWNLOADS_1_RHC102_3` status string, and **four distinct positive hosted run IDs** named Candidate/Publisher/Downloads/RHC102. No foreign Issue, unknown JSON fields, forged roles, extra suffix, malformed or noncanonical content may be sent. Immediately before the one POST, recheck remote Issue is open and canonical, current main SHA, latest published version/source SHA, and the complete comment inventory containing **no existing Fast audit record**. Hardcode `gh api -X POST repos/<owner>/<repo>/issues/<bound number>/comments --input -`, with input limited to `{"body":<exact record>}`. Never print API stderr, bodies, credentials or GH_TOKEN.

A failed, ambiguous or malformed POST result is **never replayed blindly**: the caller performs one fresh GET of the Issue comments and accepts only **one exact matching persisted record** and exactly one Fast audit prefix; an absent, duplicate or conflicting record stops closure. If the exact record already exists, the caller performs no POST and can safely resume, verifying remaining gates and Issue state. No GitHub Issues comment compare-and-swap exists, so this is guarded idempotent readback, **not a claim of transactional atomicity**. A real closed/completed Issue is accepted only with the exact previously saved audit record and repeated full original read-only evidence. Never bypass host job counts, HEAD source, UAC confirmation, signing policy or the public RHC-102 verification.
